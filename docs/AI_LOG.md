# AI-log — Alert Regimes (людина + AI)

Документ описує основні рішення в процесі підготовки до KSE Agentic School, а не заявляє, що AI безпомилково виконав усю роботу. Дати — 10–12 жовтня 2026 року.

| Етап | Що запропонував / зробив AI | Що перевіряла або вирішувала людина | Висновок |
|---|---|---|---|
| Дані | Запропонував обробляти інтервали Volunteer CSV у часовій зоні Europe/Kyiv, формувати щоденні години та аудит `naive`. | Уточнила ціль — саме зафіксована активність, не офіційний рівень загрози. | Відмовилися називати категорії офіційними жовтим/червоним рівнями. |
| Вибір регіонів | Код перевіряє критерії на 180-денному навчальному відрізку. | Наполягла на поясненні вибору семи областей на першій сторінці. | Відбір — сфокусований дослідницький, не рейтинг небезпечності. |
| Пороги та валідація | Початковий підхід вимагав ревізії часових меж. | Помітила, що написані на екрані періоди порогів і валідації перекриваються. | Для вибору моделі застосовані раніші пороги до 14.08, а для фінального тесту — пороги до 11.09. |
| Моделі | Запропонував порівняти частотну Baseline та багатокласову Logistic Regression за Brier score. | Запитала, чому Чернігівщина має однакові ймовірності на всі дні. | Це властивість Baseline, а не причина штучно модифікувати числа. Обираємо один алгоритм на область на основі попередньої валідації. |
| Технічне оточення | `scikit-learn` викликала Windows Application Control DLL policy. | Надіслала traceback. | Переписано Logistic Regression на NumPy; **не вимикали політики безпеки**. |
| Прототип і UX | Перший Streamlit показував занадто багато щоденних значень одночасно. | Обрала інтро-дисклеймер, календарні кнопки прогнозу, історичну теплову карту та категорії замість перемикання областей. | Історія — 7 областей × 12 місяців; деталізація — одна область, місяць, 01–31, без 06 AM на X. |
| Додаткові тести | AI запропонував ранні rolling-origin вікна для Чернігівської, Сумської, Запорізької. | Просила не міняти модель лише заради різних відсотків. | Ранні результати були неоднозначними, тому фінальний вибір не змінено. |
| Data leakage | Спочатку прогноз був зі зрізу 09.10. Зі свіжого CSV з'явилися записи 10–12.10. | Сама вказала: використовувати 12 жовтня для прогнозу 12–18 було б leakage. | Впроваджено `safe_week.py`: суворий бар'єр 00:00, обрізка інтервалів через опівніч, інваріантність до майбутніх даних. |
| Автоматизація | Запропонував завантажувати CSV автора через raw GitHub URL, щонеділі запускати GitHub Actions. | Створила окремий репозиторій `alert-regimes`. | Нові прогнози повинні публікуватися лише за достатньої історії, з маніфестом та дисклеймером про publication timestamps. |

**Реальні виправлення:** спершу виявили Windows `ImportError` із заблокованими DLL; тест `import numpy` не гарантував, що працює `numpy.random` або `pandas`. Потім виявили несумісність написаних періодів і фактичних меж оцінювання, виправили протокол. У Streamlit базовий datetime-графік під час масштабування показував `06 AM`, `12 PM`; замінили X на числа днів, покращили товщину стовпчиків та tooltip.

**Що може бути помилкою AI і потребує людської перевірки:** твердження про повноту CSV без часу публікації окремих рядків, оцінка якості на повторно використаному holdout, інтерпретація категорій як реальної небезпеки. Тому збережено окремий audit та часові обмеження; не представлено результат як офіційний прогноз ризику.

**Перевірка збірки:** локальне збирання фінального комплекту виконувалося окремо, із повторним `run_data.py`, `run_regimes.py`, `run_forecast.py` і тестами. Автоматизація GitHub Actions потребує перевірки в GitHub після завантаження репозиторію. Сам браузерний UI потрібно додатково перевірити вручну.
