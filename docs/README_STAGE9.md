# Stage 9 — Автоматичний щотижневий прогноз Alert Regimes

## Що реалізовано

`weekly_autorun.py` завантажує **безпосередньо з репозиторію автора** файл:

`https://raw.githubusercontent.com/Vadimkin/ukrainian-air-raid-sirens-dataset/main/datasets/volunteer_data_en.csv`

Це пряме посилання на той самий файл, який у браузері відкривається за посиланням `github.com/Vadimkin/.../blob/main/datasets/volunteer_data_en.csv`.

Джерело: https://github.com/Vadimkin/ukrainian-air-raid-sirens-dataset (зазначити автора у фінальному README).

Планувальник `.github/workflows/weekly-forecast.yml` запускається **щонеділі о 18:00 UTC** (20:00 за Києвом узимку, 21:00 влітку): **до початку наступного понеділка**. Скрипт автоматично визначає наступний понеділок, завантажує CSV, перевіряє структуру, відсутність критичних помилок, свіжість, фіксує завершену історію та формує прогноз **пн–нд** для 7 областей.

- Якщо джерело на недільному вечірньому запуску вже містить початки тривог у неділю, `suggested_last_day` обережно дозволить використовувати **суботу включно**. Тоді горизонти — **2–8**, а неділя не потрапляє до моделі. Якщо останній початок тривоги був лише в суботу, зріз може бути п'ятниця, горизонти **3–9**. Обидва варіанти залишаються в межах історично перевірених горизонтів.
- Якщо джерело надто старе (останній горизонт > 9), скрипт **завершиться з помилкою, не публікуватиме прогноз**. Не вигадує відсутні дані.
- Якщо запізнився до початку тижня, скрипт також відмовляє в публікації прогнозу заднім числом.
- Пороги (`outputs/regime_thresholds.csv`) і вибір моделі (`outputs/model_selection.csv`) **заморожені**: вибір не робиться на нових даних, щоби не підганяти результати.
- Завантажений великий CSV не додається до Git — у маніфесті є SHA-256 знімка, дата запуску та всі важливі часові межі. Не можна довести повноту подій лише за наявністю останньої дати; це чесно позначено в маніфесті.
- Прогнозні файли додаються до `analysis/auto_forecasts/YYYY-MM-DD/` і `outputs/auto_week_latest.csv` з `outputs/auto_week_latest_manifest.json`. **Старі `outputs/week_2026-10-12_to_18.csv` і `forecast_manifest.json` ніколи не перезаписуються.**

> **ВАЖЛИВО:** нинішній Streamlit Stage 7 поки *не читає* `auto_week_latest.csv`. Це окремий крок інтеграції інтерфейсу! Stage 9 реалізує автоматичне **отримання даних і створення результату**, а не автоматичну зміну візуалізації. Не стверджуйте, що вже є онлайн-прогноз у Streamlit, поки не оновлено `app.py`.

## Додавання в наявний PyCharm-проєкт

Потрібні завершені Stage 8 і Stage 7, а також `data.py`, `regimes.py`, `forecast.py` (NumPy fallback), `pure_numpy_logistic.py`, `safe_week.py` та обидва CSV з вибором моделі й порогами в `outputs/`.

1. Зробіть резервну копію проєкту і `outputs/`.
2. У Stage 9 замініть **лише** `safe_week.py` (сумісне розширення Stage 8), додайте `weekly_autorun.py`, `requirements_auto.txt`, `README_STAGE9.md`.
3. Додайте `tests/test_weekly_autorun.py` до тестів. `tests/test_safe_week.py` з Stage 8 збережіть.
4. Для GitHub покладіть `.github/workflows/weekly-forecast.yml` **з точною структурою папок**.
5. Запуск у PyCharm (робочий `python`, не заблокована `.venv`):

```powershell
python -m pip install -r requirements_auto.txt
python -m pytest -q tests/test_safe_week.py tests/test_weekly_autorun.py
python weekly_autorun.py --check-source
```

`--check-source` лише перевірить пряме підключення до CSV. **Не робіть сьогодні `python weekly_autorun.py` у понеділок 12 жовтня й не очікуйте прогнозу 19–25 жовтня:** джерело поки не містить даних до необхідного зрізу, скрипт коректно відмовить. Перший нормальний тижневий запуск очікується **в неділю 18 жовтня**.

## Створення нового GitHub-репозиторію

Твій наявний `ukrainian-air-raids-analysis` — **інший проєкт**, не змінюй його.

1. На GitHub натисни `+` → **New repository** і створи **публічний** `alert-regimes`. Для простого перенесення локального проєкту можна створити порожній repo, без автоматично згенерованого README.
2. Завантаж до нього очищений код проєкту: `app.py`, `dashboard*.py`, `data.py`, `regimes.py`, `forecast.py`, `pure_numpy_logistic.py`, `safe_week.py`, `weekly_autorun.py`, `run_*.py`, `tests/`, `requirements*.txt`, README, AI-log, reflection, `.github/workflows/weekly-forecast.yml` і **необхідні на старті перевірені** `outputs/`.
3. **Не публікуй** `.venv/`, `__pycache__/`, зайві файли `(2)`, ноутбуки іншого проєкту, необмежені тимчасові файли. Не переплутай джерело Volunteer з вихідними результатами. Перевір ліцензію/атрибуцію автора даних.
4. У GitHub: **Actions** → знайди `Weekly Alert Regimes forecast` → перевір, чи workflow увімкнено. Потрібен дозвіл `GITHUB_TOKEN` писати до вмісту репозиторію (`permissions: contents: write` у workflow і відповідні політики репозиторію).
5. Заплановані GitHub Actions не гарантують запуск рівно у визначену хвилину. Скрипт відхилить запуск після початку тижня; це захист від помилкового «прогнозу заднім числом». У разі затримки потрібно повторно запланувати майбутній тиждень, а не потай переписувати старий.

На GitHub Actions використовується **Ubuntu та Python 3.12**, тож обмеження DLL Windows не стосуються цього середовища.

## Data leakage та якість

`forecast_from_records(..., as_of=origin)` тепер відсікає інтервали **одразу після `origin`**, а не тільки після першої прогнозної дати. Це потрібно для суботнього зрізу, коли прогноз починається в понеділок. Якщо тривога перетнула північ, її кінець обрізається до межі. Тести перевіряють, що додавання недільних/прогнозних рядків не змінює імовірностей **ані Baseline, ані Logistic Regression**.

**Застереження:** добровільний CSV не містить моменту публікації кожної події. Автоматичний запуск фіксує час *завантаження знімка*, але не доводить повноту історичних записів. Програма прогнозує статистичну **відносну категорію записаної тривалості тривог**, а не реальний рівень небезпеки й не замінює офіційних попереджень.

## Перевірки перед демонстрацією KSE

- 9 початкових Stage 8 тестів повинні пройти;
- нові тести Stage 9 перевіряють календар Kyiv, горизонти 2–8, відмову на застарілих даних, незмінність обох моделей при зміні майбутнього, захист архіву від перезапису;
- зміна інтерфейсу для читання `auto_week_latest.csv` потребує окремого тесту відповідності маніфесту та семи календарних дат.

**Про статус:** код підготовлено та перевірено локально на збереженому CSV через підмінений завантажувач. **Живий запуск GitHub Actions ще не здійснено**, оскільки нового репозиторію `alert-regimes` наразі немає.
