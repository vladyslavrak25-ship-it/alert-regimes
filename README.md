## Модель і чесний протокол

- **Три категорії** визначені індивідуальними квантилями `q33` і `q75` за 180 навчальними днями. Застосування цих порогів до 2022–2025 років є **ретроспективним аналізом**, а не «прогнозом минулого».
- **Baseline:** частоти категорій за попередні 28 днів зі згладжуванням. Однакові числа на кожен день прогнозного тижня — очікувана властивість, бо модель не враховує день тижня.
- **Logistic Regression:** багатокласова softmax-модель на NumPy (без scikit-learn), ковзне вікно до 365 навчальних днів, ознаки тільки з минулого та з майбутньої календарної дати.
- **Вибір моделі:** до фінального тесту, за Brier score на 15.08–11.09.2026. Для цієї валідації пороги обчислені лише за історією до 14.08; перетину валідаційних днів із її порогами немає. Остаточні пороги — до 11.09, тест — 12.09–09.10. 5 областей обрали Baseline, 2 — Logistic Regression. **На одну область публікується лише один обраний алгоритм**; інший збережений як експеримент.
- **Якість:** multiclass Brier score — сума трьох квадратів помилок ймовірностей, менше краще. Відбір і тест не використовують показники прогнозних днів як ознаки; тести перевіряють інваріантність до майбутніх записів.
- **Обмеження:** вже переглянутий у старій версії holdout не є абсолютно недоторканим; відсутні історичні timestamp публікації/редагування кожного запису. Два варіанти тестування з різними горизонтами не незалежні.

## Прогноз із часовою межею

Архівна версія `outputs/week_2026-10-12_to_18.csv`: зріз **09.10.2026**, горизонти 3–9. Раніші дані використані для навчання, але **жодні події 12–18 жовтня не беруть участі в прогнозі**.

Окремий запуск на новішому знімку, якщо історія достатня:

```bash
python run_safe_week.py --csv data/volunteer_data_en_candidate.csv --start 2026-10-12
```

Файл `data/volunteer_data_en_candidate.csv` навмисно не публікується як гарантовано наявний до 12 жовтня. Якщо його використати зараз, отриманий результат **ретроспективна реконструкція**, а не доказ прогнозу, зробленого до початку тижня. `safe_week.py` обрізає записи рівно на 00:00 першого прогнозного дня, перевіряє перетини опівночі та не використовує події прогнозних дат.

## Автоматизація з GitHub Actions

`.github/workflows/weekly-forecast.yml` виконує `weekly_autorun.py` щонеділі о **18:00 UTC** (20:00/21:00 за Києвом), до початку наступного понеділка. Він завантажує актуальний Volunteer CSV за [прямим посиланням](https://raw.githubusercontent.com/Vadimkin/ukrainian-air-raid-sirens-dataset/main/datasets/volunteer_data_en.csv), перевіряє схему, свіжість, відсутність майбутніх днів та оцінений горизонт **не довший ніж 9 днів**, використовує заморожені пороги й вибір моделі, зберігає тижневий маніфест і контрольні суми.

Якщо джерело застаріле — **новий прогноз не публікується**. Автоматизація не гарантує точного часу доставки та повноти джерела. Повна відтворюваність «що було видно в минулому» обмежена доступністю знімків. Після першого успішного тижневого запуску Streamlit покаже перемикач між архівним і останнім автоматичним прогнозами.

Перевірити доступність джерела без випуску прогнозу:

```bash
python weekly_autorun.py --check-source
```

У GitHub відкрийте **Actions → Weekly Alert Regimes forecast → Run workflow** для ручного тестування. *У понеділок він обиратиме наступний понеділок, а не перераховуватиме поточний тиждень заднім числом.* Для запису результатів workflow потребує права `contents: write` (вказане в YAML та має бути дозволене налаштуваннями репозиторію).

## Висновки та подальша робота

Модель не обов'язково стає кращою, якщо прогнозовані відсотки змінюються щодня. Baseline може бути точнішою від складнішої Logistic Regression на даних конкретної області. Потрібно окремо перевіряти інші ковзні вікна й періоди, оцінювати якість на *нових* тижнях та дослідити часову доступність джерела.
